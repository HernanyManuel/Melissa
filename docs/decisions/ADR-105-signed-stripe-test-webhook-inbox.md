# ADR-105 — Stripe: receção HMAC v1 em modo test e event inbox sem processamento

## Estado e motivação

Phase 9, incremento após ADR-104; branch `feature/phase-8-inbox`, PR #7 draft, schema **64**. O objetivo é receber e guardar **com segurança, sem efeitos financeiros** os eventos Stripe de teste previstos no §45, antes de implementar a reconciliação e o modelo de entitlement. Os eventos de assinatura não são prova suficiente para faturação automática sem consulta e mapeamento de provider.

## Contratos e limites

1. A rota pública `POST /webhooks/stripe` está **desabilitada por omissão**, respondendo 404, e exige `STRIPE_WEBHOOK_ENABLED=true` mais `STRIPE_WEBHOOK_SECRET=whsec_...` em ambiente de teste para aceitar chamadas. Não é necessária API key Stripe, não se efetuam pedidos externos ou cobranças. O segredo não é incluído em logs/respostas. Um handler sem segredo falha 503.
2. O parser `express.raw` (JSON, 256 KiB, `inflate:false`) corre antes do parser global Nest. A verificação usa HMAC-SHA256 sobre `t + '.' + originalBuffer`, com `Stripe-Signature` contendo um único `t` canónico de 10–11 dígitos e até oito `v1` hexadecimais. A tolerância é ±300 s e cada assinatura candidata tem tamanho constante na comparação com `timingSafeEqual`. A verificação ocorre **antes de JSON.parse**, nunca por reserialização.
3. Apenas envelopes bem formados contendo ID `evt_`, tipo limitado, `created` Unix válido, `livemode=false` e `data.object` JSON objeto são aceites. **Live mode é rejeitado**, até quando a assinatura é válida. Os tipos permitidos são `checkout.session.completed`, `customer.subscription.created|updated|deleted`, `invoice.paid`, `invoice.payment_failed`. Outros tipos assinados recebem ACK sem armazenamento para evitar retries inúteis.
4. A tabela global `stripe_webhook_events` é explicitamente **não tenant-assigned**: um webhook autentica um endpoint Stripe, não a associação de `metadata.tenant_id` a uma empresa. Tem ID único, tipo, `api_version`, carimbo provider, digest hex SHA-256 dos bytes recebidos, `payload JSONB`, `livemode=false`, `status='received'` fixo e `received_at`. `ON CONFLICT DO NOTHING` guarda uma entrega uma vez; um novo envio de mesmo ID e hash/tipo coincide e é ACK idempotente, mas uma colisão com corpo divergente responde 409 **sem alterar o registo original**.
5. `stripe_webhook_events` usa **RLS ENABLE/FORCE**. `melissa_runtime` tem apenas INSERT em colunas allowlisted e SELECT de `event_id,event_type,payload_sha256`; NÃO possui SELECT do `payload`, do status ou de data privada, nem UPDATE/DELETE. Não há endpoint GET do event inbox, nem mutação de `plans`, `subscriptions` ou contas; JSON pode conter PII e ficará reservado a um reconciliador separado com role privilegiado, auditoria, retenção e encriptação/segredos a definir.
6. HTTP ACK 200 é apenas aceitação de transporte; 400 invalid envelope, 403 signature, 409 collision, 413 oversized, 415 wrong media type e 503 persistence/unavailable. Nunca confundir `received` com `processed`; não existe worker nem transição automática para estado billing validado. `entitlements.automationEnabled=false`, `billingVerified=false` e blocker de onboarding continuam intactos. Health/readiness exige schema 64.

## Validação e limitações

Suite de integração real Nest + PostgreSQL/RLS sob runtime role e admin test fixture, incluída em `pnpm test:integration`. Cobre autenticação HMAC incorreta/ausente, timestamp claramente antigo/futuro, media type, JSON inválido, rejeição `livemode=true`, assinatura múltipla (candidata errada e válida), evento assinado desconhecido ignorado, 1ª inserção, replay idempotente, colisão de ID diferente, digest, payload sensível só legível com role privilegiado, RLS/grants, não atribuição ao tenant indicado em metadata e zero alterações de subscrição. CI no HEAD final a validar.

**Próximas fases separadas:** credenciais de teste e validação com Stripe CLI/provider real, event delivery rate-limiter, event retention/redaction, reconciliador sob role distinto que consulta o provider e resolve ownership por identificadores Stripe previamente criados em Checkout, idempotent outbox/worker, transições monotónicas, Checkout/Portal, limites e CostGuard. **Não** ativar webhook live, não autorizar pagamento com base no corpo do evento isoladamente, não modificar os endpoints owner/admin já existentes. O modelo de planos de ADR-104 mantém-se inalterado.
